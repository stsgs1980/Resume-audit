# SPEC-pipeline: этапы, ядро, LLM-слой

Часть спецификации Resume Audit.
См. также: [SPEC.md](SPEC.md), [SPEC-facts.md](SPEC-facts.md).

## 1. Трёхслойная архитектура

| Слой       | Ответственность                                    | Реализация               |
| ---------- | -------------------------------------------------- | ------------------------ |
| Ядро       | Арифметика, даты, блок-листы, кросс-проверка чисел | TypeScript, без LLM      |
| Извлечение | Разбор формулировок, подтверждение навыка          | LLM, узкие JSON-схемы    |
| Генерация  | Три версии резюме, план, вопросы                   | LLM, числа из facts.json |

### 1.1. Счётчики вызовов LLM

| Тип                             | Значение                    |
| ------------------------------- | --------------------------- |
| Логических вызовов без вакансии | 8                           |
| Логических вызовов с вакансией  | 9                           |
| Транспортных попыток            | логические x retryCount (2) |

Логические вызовы: этап 2 — 1, этап 5 — 1, этап 6 — 1 (если вакансия),
этап 7 — 3, этап 8 — 3.

Алерт: больше 11 логических вызовов за прогон — признак архитектурной
ошибки.

### 1.2. Почему модель не считает

Модель на бесплатном уровне ошибается в арифметике, путает даты
и выдумывает навыки. Всё, что считается регулярным выражением или
арифметикой, модели не отдаётся.

## 2. Этапы конвейера

Восемь модулей. Этапы 1, 3 не требуют LLM.

| Этап | Название                | Исполнитель | Выход                |
| ---- | ----------------------- | ----------- | -------------------- |
| 1    | Инвентаризация          | Код         | files.json           |
| 2    | Извлечение утверждений  | LLM         | claims.json          |
| 3    | Детерминированный аудит | Код         | audit.json           |
| 4    | Разрешение вопросов     | Человек     | facts.json, evidence |
| 5    | Оценка ролей            | LLM         | audit.json (roles)   |
| 6    | ATS-анализ              | LLM + код   | audit.json (ats)     |
| 7    | Генерация               | LLM         | resumes/*.json       |
| 8    | Верификация             | Код + LLM   | validation.json      |

### 2.1. Гейт перед LLM

Пока тесты ядра не зелёные, этапы 2, 5, 6, 7, 8 не запускаются.

Сломанное ядро под LLM означает документы с выдуманными числами.

### 2.2. Этап 4 — человек в цикле

Очередь вопросов `open_questions` с полями ответа. Человек заполняет
карточку `evidence`. Статус `needs_evidence` закрывается только при
заполненных обязательных полях карточки.

При возврате приложение показывает «Продолжить с вопроса N из M».
Частичные ответы сохраняются сразу.

Один прогон = один `run_id`. Параллельные прогоны над одним `facts.json`
блокируются через lock-файл.

### 2.3. Locking фактов

`facts.json` имеет состояние `draft | locked`. Генерация и экспорт —
только из `locked`.

Переход в `locked` требует:

- нет открытых `needs_evidence`;
- все evidence `confirmed`;
- `share_of_applications` валидна.

Разблокировка требует причины и переводит все производные в `stale`.

### 2.4. Опциональный hh-парсер

HTML-выгрузка резюме с hh.ru и TXT/RTF-экспорт имеют предсказуемую
структуру классов (`.resume__title`, `.resume__position`,
`.resume-experience`, `.resume-experience__company`, `.resume-education`,
`.resume-skils`).

Опциональный детерминированный парсер `src/core/hh-parser.ts` может
за миллисекунды собрать скелет `facts.json` без LLM.

Статус: опциональный ускоритель, не основной путь. Основной —
универсальный LLM-парсер через Этап 2. Причина: hh.ru может менять
разметку, парсер придётся поддерживать.

## 3. Детерминированное ядро

### 3.1. Даты и стаж

Реализация по [SPEC-dates.md](SPEC-dates.md).

Обязательно обе величины: наивная сумма и объединение интервалов.

Дополнительные проверки:

- разрывы больше 3 месяцев — предупреждение с точными датами;
- пересечения у ролей с разными `overlap_group` — предупреждение;
- совпадение `end` одной роли и `start` другой — норма, не пересечение;
- расхождение с заявленной длительностью больше 1 месяца — фиксировать.

### 3.2. Нормализация чисел

Извлечение значения и единицы: `4,2 млн`, `4.2 млн`, `4 200 000`,
`120 тыс.`, `$1,02 млн`, `45%`.

Валюта извлекается из контекста строки:

- `RUB`, `руб` -> RUB;
- `$`, `USD`, `доллар` -> USD;
- `EUR` -> EUR;
- отсутствует -> `null` с флагом «валюта не указана».

Никогда не подставлять валюту по умолчанию.

Кросс-проверка чисел между версиями:

1. Извлечь все числа с контекстом.
2. Сгруппировать кандидатно по ключу (компания, тип метрики).
3. Группировка требует подтверждения LLM.
4. Пороги расхождения: меньше 2% — предупреждение; 2% и больше —
   жёсткое расхождение с блокировкой.
5. `~4 млн` против `4,2 млн` — предупреждение «возможно округление».

### 3.3. Блок-лист навыков per-role

Структура в конфиге:

```text
skillRules: {
  always: [ /* требует доказательства во всех ролях */ ],
  sales: [ /* ... */ ],
  salesops: [ /* ... */ ],
  aipo: [ /* ... */ ]
}
```

Разделение кода и LLM обязательно:

1. Код: нормализация текста и поиск вхождений навыка в тексте опыта.
2. LLM: подтверждение применения — есть ли рядом действие и результат.

Результат по каждому навыку: «подтверждён пример» / «вхождение есть,
применение не описано» / «не найден вовсе».

Только первый статус допускает навык в резюме без оговорки.

### 3.4. Маркеры завышенного AI-позиционирования

Ищутся во всём тексте, не только в навыках: `production`,
`production-ready`, `RAG-система`, `multi-agent`, `LangChain`,
`подтверждённый ROI`, `исключение риска`, `готов к переводу в продукт`.

Каждое вхождение -> флаг с решением: оставить, переформулировать, удалить.

### 3.5. Детектор плейсхолдеров

Регулярные выражения из конфига: `+7 (XXX)`, `email@example.com`,
`(Указать...)`, `@username`, `[cite: N]`, `Lorem ipsum`.

Найдено -> файл `flagged_synthetic`, данные не используются.

### 3.6. Структура заголовка и полей hh.ru

- Слэш в тайтле -> предупреждение: одно резюме = одна должность.
- Более одной специализации -> предупреждение.
- Тайтл не совпадает с целевой ролью -> предупреждение.
- Отсутствие обязательных полей -> предупреждение со списком.
- Проверка обязательных полей применяется и к сгенерированным версиям.

### 3.7. ATS-проверка в контексте

- Списки ключевых слов в конфиге для каждой роли.
- Каждое обязательное ключевое слово проверяется в тексте опыта.
- Три категории: «в опыте», «только в навыках», «отсутствует».
- Вакансия загружена -> извлечение ключевых слов LLM со схемой
  `{ keyword, category, is_mandatory, quote }`. Цитата обязательна.
- Вакансии нет -> типовой профиль из конфига, пометка «гипотеза».

### 3.8. Детектор прогнозных метрик

Маркеры: `снизится`, `сократится`, `достигнет`, `планируется`,
`ожидается`, `целевая`, `гипотеза`, `прогноз`, `потенциально`.

- Число рядом с маркером -> флаг «целевая метрика, не результат».
- Число без маркера в блоке результатов -> флаг «проверить: измеренное
  или прогнозное».
- Число из `target_metrics` портфельного проекта никогда не появляется
  в блоке результатов.

### 3.9. Детектор недоказанной причинности

Обобщённый, не только под клиент+выручка+процент.

Правило: любой количественный эффект, приписанный другой стороне
(клиент, отдел, компания, партнёр, отрасль), подаётся как достигнутый,
если рядом нет маркера источника.

Маркеры источника: `по данным`, `по результатам замера`, `по отчётности`,
`по данным компании`, `отчётность компании`, `источник данных`.

Маркеры однозначной причинности, требующие оговорки: `благодаря`,
`в результате`, `за счёт`, `позволило`, `обеспечило`.

## 4. LLM-слой

### 4.1. Клиент

`@opencode-ai/sdk`. Версия зафиксирована точно в `package.json`.

При старте — health-check. Если сервер недоступен, приложение работает:
все детерминированные проверки доступны, LLM-этапы заблокированы.

### 4.2. Сессия

Одна сессия на прогон. Создаётся явно.

Перед каждым этапом — проверка живости. При ошибке — пересоздание
и продолжение с последнего чекпоинта.

### 4.3. Structured output

Ответ строго по JSON Schema.

Если данных недостаточно — вернуть пустой массив и
`status: "needs_evidence"`. Не выдумывать значения.

Общие правила для всех промтов:

- ответ строго по JSON Schema, без текста вокруг JSON;
- запрещено вводить числа и навыки, отсутствующие во входных данных;
- инструкция: «Если ты не можешь ответить на основании входных данных —
  верни пустой массив. Это правильнее, чем придумать».

### 4.4. Чекпоинт

Перед каждым этапом состояние пишется в `stage-state.json` как `running`.
После — `completed` или `failed`.

Оборванный вызов сохраняет частичный ответ в
`data/partial/<stage>-<ts>.json`.

При повторном запуске приложение предлагает продолжить с последнего
`completed`.

### 4.5. Логирование

Все вызовы: этап, модель, длина промта и ответа, время, число попыток,
успех.

Ротация `model-responses.log` по размеру 5 МБ, хранить 3 файла.
Содержимое резюме в лог не пишется.

### 4.6. Gap-to-Question Generator

Если у пользователя один файл резюме, противоречий между файлами нет,
но резюме может быть слабым под целевую вакансию.

Алгоритм:

1. Пользователь загружает резюме и 1–3 текста целевых вакансий.
2. Детерминированный ATS-модуль (`src/core/ats.ts`) находит обязательные
   требования вакансии, которых нет ни в `facts.json`, ни в опыте.
3. Система создаёт вопрос на Этапе 4: «В целевой вакансии требуется: "X".
   В вашем резюме это не упомянуто. Был ли у вас подтверждённый опыт?»
   Варианты ответа:
   - Да, добавить факт и заполнить карточку evidence.
   - Нет, никогда не приписывать этот навык в резюме.
4. Ответ пользователя либо создаёт новый факт, либо оставляет навык
   в чёрном списке для этой роли.

Это делает приложение полезным для одного файла резюме.

### 4.7. Схемы ответов LLM

API 2.0.28 не имеет structured output. Мы просим LLM вернуть JSON
в тексте ответа, извлекаем его, парсим и валидируем Zod-схемой.
Схемы живут в `src/llm/schemas.ts`, реестр промтов — в
`src/llm/prompt-registry.ts`. При неуспехе — ретрай, затем
локальный `StructuredOutputError`.

#### 4.7.1. extractionResponseSchema (промт extraction)

Назначение: извлечение утверждений из исходных файлов (этап 2).

Форма: `{ claims: [...] }`. Поля claim: `statement`, `quote`
(min 1), `source_file`, `category` (employment | result | skill |
tool | education | language | project | link), `metric_type`,
`number` (или null), `currency` (RUB | USD | EUR или null),
`status` (confirmed | needs_evidence | remove), `reason`.

Особенность: `quote` обязателен — утверждение без дословной цитаты
отбрасывается кодом и не попадает в ответ.

#### 4.7.2. rolesResponseSchema (промт roles)

Назначение: оценка кандидата под целевые роли (этап 5).

Форма: `{ roles: [...] }`. Поля: `role_id`, `scores` (6 метрик
0..10: experience_fit, responsibility_level, measurable_results,
keyword_fit, hr_screen, hiring_manager), `total`, `strengths[]`,
`gaps[]`, `overpositioning_risk` (0..10), `recommendation`.

#### 4.7.3. resumeResponseSchema (промты generation_*)

Назначение: генерация версии резюме (этап 7). Три промта:
generation_sales, generation_salesops, generation_aipo — одна
схема на всех.

Форма: `title`, `specialization`, `employment_type`, `work_format`,
`experience_total`, `experience_as_of`, `about`, `jobs[]`,
`skills[]` (`{ skill, skill_id }`), `languages[]`. Поля job:
`job_id`, `company`, `industry`, `position`, `period`, `duration`,
`context`, `actions[]`, `results[]`,
`total_experience_inconsistent`, `total_experience_note`.

Каждый result обязан иметь `fact_id` (min 1) — иначе число
не трассируется к факту и блокируется верификацией.
`hedge_present: bool` фиксирует наличие оговорки рядом с числом.

#### 4.7.4. verificationResponseSchema (промт verification)

Назначение: слой 2 верификации (этап 8, дополнение к коду).

Форма: `{ checks: [...], unsupported_skills: [], forbidden_words_found: [] }`.
Поля check: `number`, `claim`, `matches_fact`, `fact_id`
(или null), `matches_role`, `has_hedge`, `verdict`, `comment`.
`verdict`: ok | unsupported_number | wrong_role | missing_hedge |
is_target_metric.

#### 4.7.5. Реестр промтов

Все id промтов и их версии:

- extraction v1
- roles v1
- generation_sales v1
- generation_salesops v1
- generation_aipo v1
- verification v1

Файлы промтов: `config/prompts/<id>.v<version>.md`.
Загрузчик: `src/llm/prompts.ts` (`loadPrompt`, `listPrompts`).
Реестр: `src/llm/prompt-registry.ts`, функция `getPromptSpec(id)`.
