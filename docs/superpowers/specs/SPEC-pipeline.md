# SPEC-pipeline: этапы, ядро, LLM-слой

Часть спецификации Resume Audit.
См. также: [SPEC.md](SPEC.md), [SPEC-facts.md](SPEC-facts.md).

## 1. Трёхслойная архитектура

| Слой       | Ответственность                                    | Реализация               |
| ---------- | -------------------------------------------------- | ------------------------ |
| Ядро       | Арифметика, даты, блок-листы, кросс-проверка чисел | TypeScript, без LLM      |
| Извлечение | Разбор формулировок, подтверждение навыка          | LLM, узкие JSON-схемы    |
| Генерация  | Три версии резюме, план, вопросы                   | LLM, числа из facts.json |

### 1.1. Счётчики вызовов LLM

| Тип                             | Значение                    |
| ------------------------------- | --------------------------- |
| Логических вызовов без вакансии | 8                           |
| Логических вызовов с вакансией  | 9                           |
| Транспортных попыток            | логические x retryCount (2) |

Логические вызовы: этап 2 — 1, этап 5 — 1, этап 6 — 1 (если вакансия),
этап 7 — 3, этап 8 — 3.

Алерт: больше 11 логических вызовов за прогон — признак архитектурной
ошибки.

### 1.2. Почему модель не считает

Модель на бесплатном уровне ошибается в арифметике, путает даты
и выдумывает навыки. Всё, что считается регулярным выражением или
арифметикой, модели не отдаётся.

## 2. Этапы конвейера

Восемь модулей. Этапы 1, 3 не требуют LLM.

| Этап | Название                | Исполнитель | Выход                |
| ---- | ----------------------- | ----------- | -------------------- |
| 1    | Инвентаризация          | Код         | files.json           |
| 2    | Извлечение утверждений  | LLM         | claims.json          |
| 3    | Детерминированный аудит | Код         | audit.json           |
| 4    | Разрешение вопросов     | Человек     | facts.json, evidence |
| 5    | Оценка ролей            | LLM         | audit.json (roles)   |
| 6    | ATS-анализ              | LLM + код   | audit.json (ats)     |
| 7    | Генерация               | LLM         | resumes/*.json       |
| 8    | Верификация             | Код + LLM   | validation.json      |

### 2.1. Гейт перед LLM

Пока тесты ядра не зелёные, этапы 2, 5, 6, 7, 8 не запускаются.

Сломанное ядро под LLM означает документы с выдуманными числами.

### 2.2. Этап 4 — человек в цикле

Очередь вопросов `open_questions` с полями ответа. Человек заполняет
карточку `evidence`. Статус `needs_evidence` закрывается только при
заполненных обязательных полях карточки.

Этап 4a пишет `facts.json` только при успешной валидации схемы
(fail-closed): при `schema_mismatch` файл не пишется, итог несёт
`written: false` и ошибки Zod в warnings.

После успешной записи 4a обновляет хеши (`facts_hash`, `meta_hash`)
в `audit.json`, если файл существует, и — при переданных `storageConfig`
и `slug` — помечает `stale` документы `stage-state.json` с прежним
`facts_hash` (инвалидация производных). Этапы 7 и 8 при генерации
и верификации пишут в `stage-state.json` актуальный `facts_hash`,
поэтому свежие документы stale не помечаются.

Порядок этапов — 3 до 4a: audit, созданный раньше фактов, несёт пустые
хеши и warning «audit создан до facts.json, hash будет заполнен при
пересчёте»; хеши заполняет 4a.

Результаты собираются с per-role allowlist: роли результата — из
`detected_roles` утверждения (пересечение с целевыми ролями; пусто —
все целевые), `hedge_required` результата — из `requires_hedge`
утверждения (по умолчанию `false`).

При возврате приложение показывает «Продолжить с вопроса N из M».
Частичные ответы сохраняются сразу.

Свободный ответ на вопрос «противоречие» и «целевая vs измеренная»
разбирается кодом: «удалить»/«целевая» — удаление факта, «не удалять»/
«оставить»/«не целевая» — подтверждение; «не оставлять» — удаление.
Отрицание проверяется раньше ключевого слова, в том числе через
служебные слова («не надо удалять»). Неоднозначный ответ факт не меняет:
ответ получает статус `deferred`, warning `answer_unclear` («ответ не
распознан, требуется уточнение») попадает в итоги этапа 4b. Валюта
ищется в тексте; не найдена — тот же warning.

Один прогон = один `run_id`. Параллельные прогоны над одним `facts.json`
блокируются через lock-файл.

### 2.3. Locking фактов

`facts.json` имеет состояние `draft | locked`. Генерация и экспорт —
только из `locked`.

Формат lock-файла един для storage и pipeline:

```json
{ "state": "draft | locked", "lockedAt": "ISO 8601 | null" }
```

`lockedAt` — время блокировки, `null` для `draft`.
Голая строка `"draft" | "locked"` — legacy, читается, но не пишется.

Переход в `locked` требует:

- нет открытых `needs_evidence`;
- все evidence `confirmed`;
- `share_of_applications` валидна.

Разблокировка требует причины и переводит все производные в `stale`.

### 2.4. Опциональный hh-парсер

HTML-выгрузка резюме с hh.ru и TXT/RTF-экспорт имеют предсказуемую
структуру классов (`.resume__title`, `.resume__position`,
`.resume-experience`, `.resume-experience__company`, `.resume-education`,
`.resume-skils`).

Опциональный детерминированный парсер `src/core/hh-parser.ts` может
за миллисекунды собрать скелет `facts.json` без LLM.

Статус: опциональный ускоритель, не основной путь. Основной —
универсальный LLM-парсер через Этап 2. Причина: hh.ru может менять
разметку, парсер придётся поддерживать.

### 2.5. Оркестратор и CLI

`src/pipeline/run.ts` экспортирует `runPipeline(params)` — сквозной
прогон этапов 1–8. Модули оркестратора:

- `run.ts` — сборка результата и артефактов;
- `run-stages.ts` — этапы 1–4 и отметки 5/6;
- `run-stages-llm.ts` — этапы 7–8;
- `run-context.ts` — общие помощники и пути workspace;
- `run-types.ts` — `PipelineParams`, `PipelineResult`, `PipelineStageResult`.

Правила прогона:

- этапы 2, 5, 6, 7, 8 требуют LLM. При `skipLlmStages: true` или
  `llmClient: null` этапы 2, 7, 8 получают `skipped`, а этап 3
  выполняется как 3a (детерминированная часть). Этапы 5 и 6
  показываются как `skipped` с пометкой «в составе этапа 3»;
- зависимости: этапы 2 и 3 не запускаются без `completed` этапа 1;
  этап 4a — без `completed` этапа 1 и без `failed` этапа 2, если facts
  не locked (намеренно пропущенный в skip-LLM режиме этап 2 не блокирует
  4a; locked facts доступны для генерации без повторного извлечения);
  этап 7 — только после записи `facts.json` этапом 4a; этап 8 —
  только после `completed` этапа 7 и хотя бы одного свежего резюме.
  При нарушении этап получает `skipped` с причиной;
- ошибки этапов не пробрасываются: они попадают в `stages[].error`,
  предупреждения — в `stages[].warnings`; прогон продолжается со
  следующего возможного этапа;
- `overallStatus`: `failed` — упал этап 1 или этап 3; `partial` — есть
  `failed` или пропущен один из этапов 2, 7, 8; иначе `success`.
  Заблокированный экспорт на этапе 8 даёт `failed` этапа и `partial`
  прогона;
- если `facts.json` существует и `facts.lock` в состоянии `locked`,
  этап 4 не пересобирает факты: он проверяет файл по схеме и фиксируется
  `completed` с пометкой «facts.json уже locked». Несоответствие схеме —
  `failed` этапа, файл не перезаписывается. Это сохраняет правки этапа 4b
  и позволяет повторно запустить генерацию. Для пересборки фактов из
  claims нужно сначала разблокировать facts;
- этап 4a пишет валидный пустой скелет `facts.json`, только если
  `claims.json` прочитан без ошибок, пуст и `facts.json` ещё нет.
  Если `claims.json` отсутствует, а `facts.json` тоже нет, пустой
  скелет создаётся — это режим первого заполнения и `--skip-llm`.
  Если `claims.json` отсутствует или пуст, а `facts.json` существует,
  файл не перезаписывается: этап возвращает `written: false` и warning
  `claims_missing` или `claims_empty`. Битые claims и ошибки схемы
  остаются fail-closed: файл не перезаписывается;
- при повторном прогоне 4a сохраняет `meta.candidate_name` и
  `meta.geography` из существующего `facts.json`, если параметры
  `candidateName` и `geography` не переданы. `meta.targets` всегда
  собирается из конфига ролей;
- при пересборке facts 4a сравнивает хеш существующих фактов с новыми.
  Если содержимое изменилось, `facts.lock` переводится в `draft`, после
  чего пишется `facts.json`; ошибка сброса lock отменяет запись.
  Неизменные факты сохраняют `locked`. Если переданы `storageConfig`
  и `slug`, документы с прежним `facts_hash` помечаются `stale`;
- частичный сбой этапа 7 (ошибка хотя бы по одной роли) помечает
  сгенерированные в этом прогоне документы `stale: true`; этап 8 при
  этом не запускается;
- этап 8 проверяет только версии, сгенерированные текущим прогоном;
  если свежих версий нет, этап получает `skipped`. Отсутствие
  ожидаемого файла версии и несоответствие validation-схемы — ошибки
  этапа: `verification` помечается `failed`, экспорт не подтверждается.
  `stage-state.json` обновляется на всех путях завершения, включая
  ошибки lock/чтения facts и полное отсутствие ожидаемых версий;
  ожидаемые, но не проверенные версии с существующей записью получают
  `stale: true`. Любая ошибка этапа выставляет `exportBlocked`.
  Устаревшие `validation/*.json` от прошлых прогонов не переиспользуются;
- этапы 7 и 8 запускаются только при `facts.lock` в состоянии
  `locked`. `requireLockForStage7: false` разрешает попытку запуска
  этапа 7 без предварительной проверки (сам этап 7 всё равно
  проверит lock).

CLI: `npm run pipeline`, скрипт `scripts/pipeline.ts`.

```text
npm run pipeline -- --workspace <slug> [--input <path>] [--skip-llm]
                   [--audit-date YYYY-MM-DD] [--model <id>]
```

Корень данных — `data` или `RESUME_AUDIT_DATA_DIR`. По умолчанию
workspace — первый по алфавиту каталог с допустимым slug в
`<root>/workspaces/`, вход — `<workspace>/input/`, дата — сегодняшняя,
модель — `opencode/space-bunny-free`. `--workspace` принимает только
slug `[a-z0-9_-]{1,64}` и требует существующую директорию.
`--audit-date` проверяется на формат и существование даты
`YYYY-MM-DD`. URL opencode server берётся из `OPENCODE_SERVER_URL`
(по умолчанию `http://127.0.0.1:49374`); завершающие слэши отбрасываются,
суффикс `/api` добавляется один раз. `--skip-llm` не создаёт
LLM-клиент и соответствует `skipLlmStages: true`. В `runPipeline`
передаются `storageConfig` и `slug`, чтобы пересборка facts помечала
устаревшие документы `stale`. Вывод — таблица этапов, предупреждения,
артефакты, длительность, итоговый статус. Код возврата `1`, если
`overallStatus: failed` или хотя бы один этап `failed`; skip-only
`partial` (например, `--skip-llm`) возвращает `0`.

## 3. Детерминированное ядро

### 3.1. Даты и стаж

Реализация по [SPEC-dates.md](SPEC-dates.md).

Обязательно обе величины: наивная сумма и объединение интервалов.

Дополнительные проверки:

- разрывы больше 3 месяцев — предупреждение с точными датами;
- пересечения у ролей с разными `overlap_group` — предупреждение;
- совпадение `end` одной роли и `start` другой — норма, не пересечение;
- расхождение с заявленной длительностью больше 1 месяца — фиксировать;
- date_mismatch фиксируется только между утверждениями одной компании
  (извлечение — §3.10); утверждения без компании противоречий
  не создают, общие слова компанией не считаются;
- голый год — не дата: цитата без даты месяца (confidence low)
  не создаёт работу, месяц 01 не подставляется (SPEC-dates.md §8).

### 3.2. Нормализация чисел

Извлечение значения и единицы: `4,2 млн`, `4.2 млн`, `4 200 000`,
`120 тыс.`, `$1,02 млн`, `45%`.

Валюта извлекается из контекста строки:

- `RUB`, `руб` -> RUB;
- `$`, `USD`, `доллар` -> USD;
- `EUR` -> EUR;
- отсутствует -> `null` с флагом «валюта не указана».

Никогда не подставлять валюту по умолчанию.

Кросс-проверка чисел между версиями:

1. Извлечь все числа с контекстом.
2. Сгруппировать кандидатно по ключу (компания, тип метрики).
3. Группировка требует подтверждения LLM.
4. Пороги расхождения: меньше 2% — предупреждение; 2% и больше —
   жёсткое расхождение с блокировкой.
5. `~4 млн` против `4,2 млн` — предупреждение «возможно округление».

### 3.3. Блок-лист навыков per-role

Структура в конфиге:

```text
skillRules: {
  always: [ /* требует доказательства во всех ролях */ ],
  sales: [ /* ... */ ],
  salesops: [ /* ... */ ],
  aipo: [ /* ... */ ]
}
```

Разделение кода и LLM обязательно:

1. Код: нормализация текста и поиск вхождений навыка в тексте опыта.
2. LLM: подтверждение применения — есть ли рядом действие и результат.

Результат по каждому навыку: «подтверждён пример» / «вхождение есть,
применение не описано» / «не найден вовсе».

Только первый статус допускает навык в резюме без оговорки.

### 3.4. Маркеры завышенного AI-позиционирования

Ищутся во всём тексте, не только в навыках: `production`,
`production-ready`, `RAG-система`, `multi-agent`, `LangChain`,
`подтверждённый ROI`, `исключение риска`, `готов к переводу в продукт`.

Каждое вхождение -> флаг с решением: оставить, переформулировать, удалить.

### 3.5. Детектор плейсхолдеров

Регулярные выражения из конфига: `+7 (XXX)`, `email@example.com`,
`(Указать...)`, `@username`, `[cite: N]`, `Lorem ipsum`.

Найдено -> файл `flagged_synthetic`, данные не используются.

### 3.6. Структура заголовка и полей hh.ru

- Слэш в тайтле -> предупреждение: одно резюме = одна должность.
- Более одной специализации -> предупреждение.
- Тайтл не совпадает с целевой ролью -> предупреждение.
- Отсутствие обязательных полей -> предупреждение со списком.
- Проверка обязательных полей применяется и к сгенерированным версиям.

### 3.7. ATS-проверка в контексте

- Списки ключевых слов в конфиге для каждой роли.
- Каждое обязательное ключевое слово проверяется в тексте опыта.
- Три категории: «в опыте», «только в навыках», «отсутствует».
- Вакансия загружена -> извлечение ключевых слов LLM со схемой
  `{ keyword, category, is_mandatory, quote }`. Цитата обязательна.
- Вакансии нет -> типовой профиль из конфига, пометка «гипотеза».

### 3.8. Детектор прогнозных метрик

Маркеры: `снизится`, `сократится`, `достигнет`, `планируется`,
`ожидается`, `целевая`, `гипотеза`, `прогноз`, `потенциально`.

- Число рядом с маркером -> флаг «целевая метрика, не результат».
- Число без маркера в блоке результатов -> флаг «проверить: измеренное
  или прогнозное».
- Число из `target_metrics` портфельного проекта никогда не появляется
  в блоке результатов.
- Годы не смешиваются с датами и метриками: голый год — не дата
  (SPEC-dates.md §8) и не число результата.

### 3.9. Детектор недоказанной причинности

Обобщённый, не только под клиент+выручка+процент.

Правило: любой количественный эффект, приписанный другой стороне
(клиент, отдел, компания, партнёр, отрасль), подаётся как достигнутый,
если рядом нет маркера источника.

Маркеры источника: `по данным`, `по результатам замера`, `по отчётности`,
`по данным компании`, `отчётность компании`, `источник данных`.

Маркеры однозначной причинности, требующие оговорки: `благодаря`,
`в результате`, `за счёт`, `позволило`, `обеспечило`.

### 3.10. Извлечение компании из цитаты

Компания — не пересечение слов, а результат разбора текста после
контекста «в», «в компании», «работал в», «в должности».

- Формы «ООО», «АО», «ЗАО», «ПАО», «ИП» пропускаются.
- Захватываются 1-3 слова с заглавной буквы, без кавычек.
- Название не заканчивается предлогом или союзом.
- Меньше 2 значащих символов — null.
- Нет уверенного совпадения — null; компания не угадывается.

`unknown` не создаётся: claims без компании не сливаются друг с другом,
job получает `company: ""` и warning `unknown_company`. Результат
не привязывается к job без компании.

Ограничения эвристики: топоним после «в» («в Москве») может быть принят
за компанию; падежные формы не нормализуются — «Ромашка» и «Ромашке»
считаются разными компаниями.

## 4. LLM-слой

### 4.1. Клиент

`@opencode-ai/sdk`. Версия зафиксирована точно в `package.json`.

При старте — health-check. Если сервер недоступен, приложение работает:
все детерминированные проверки доступны, LLM-этапы заблокированы.

### 4.2. Сессия

Одна сессия на прогон. Создаётся явно.

Перед каждым этапом — проверка живости. При ошибке — пересоздание
и продолжение с последнего чекпоинта.

### 4.3. Structured output

Ответ строго по JSON Schema.

Если данных недостаточно — вернуть пустой массив и
`status: "needs_evidence"`. Не выдумывать значения.

Общие правила для всех промтов:

- ответ строго по JSON Schema, без текста вокруг JSON;
- запрещено вводить числа и навыки, отсутствующие во входных данных;
- инструкция: «Если ты не можешь ответить на основании входных данных —
  верни пустой массив. Это правильнее, чем придумать».

### 4.4. Чекпоинт

Перед каждым этапом состояние пишется в `stage-state.json` как `running`.
После — `completed` или `failed`.

Оборванный вызов сохраняет частичный ответ в
`data/partial/<stage>-<ts>.json`.

При повторном запуске приложение предлагает продолжить с последнего
`completed`.

Polling ответа ассистента учитывает только части `content` с
`type: "text"`. Части `type: "reasoning"` игнорируются и не считаются
финальным ответом. Пока в сообщении нет непустой text-части, ожидание
продолжается.

### 4.5. Логирование

Все вызовы: этап, модель, длина промта и ответа, время, число попыток,
успех.

Ротация `model-responses.log` по размеру 5 МБ, хранить 3 файла.
Содержимое резюме в лог не пишется.

### 4.6. Gap-to-Question Generator

Если у пользователя один файл резюме, противоречий между файлами нет,
но резюме может быть слабым под целевую вакансию.

Алгоритм:

1. Пользователь загружает резюме и 1–3 текста целевых вакансий.
2. Детерминированный ATS-модуль (`src/pipeline/stage3/ats.ts`) находит обязательные
   требования вакансии, которых нет ни в `facts.json`, ни в опыте.
3. Система создаёт вопрос на Этапе 4: «В целевой вакансии требуется: "X".
   В вашем резюме это не упомянуто. Был ли у вас подтверждённый опыт?»
   Варианты ответа:
   - Да, добавить факт и заполнить карточку evidence.
   - Нет, никогда не приписывать этот навык в резюме.
4. Ответ пользователя либо создаёт новый факт, либо оставляет навык
   в чёрном списке для этой роли.

Это делает приложение полезным для одного файла резюме.

### 4.7. Схемы ответов LLM

API 2.0.28 не имеет structured output. Мы просим LLM вернуть JSON
в тексте ответа, извлекаем его, парсим и валидируем Zod-схемой.
Схемы живут в `src/llm/schemas.ts`, реестр промтов — в
`src/llm/prompt-registry.ts`. При неуспехе — ретрай, затем
локальный `StructuredOutputError`.

#### 4.7.1. extractionResponseSchema (промт extraction)

Назначение: извлечение утверждений из исходных файлов (этап 2).

Промт `extraction.v1.md` перечисляет допустимые значения `category`,
`metric_type`, `status` и `currency` и требует `null` для отсутствующих
чисел.

Форма: `{ claims: [...] }`. Поля claim: `statement`, `quote`
(min 1), `source_file`, `category` (employment | result | skill |
tool | education | language | project | link), `metric_type`,
`number` (или null), `currency` (RUB | USD | EUR или null),
`status` (confirmed | needs_evidence | remove), `reason`.

Опционально: `detected_roles` (какие роли явно упомянуты в контексте)
и `requires_hedge` (косвенная метрика — требуется оговорка).

Особенность: `quote` обязателен — утверждение без дословной цитаты
отбрасывается кодом и не попадает в ответ.

Ответ извлекается без клиентской schema-валидации
(`z.unknown()`), после чего `softenExtractionResponse` мягко исправляет
известные отклонения: неизвестный `category` заменяется на `result`,
неизвестный `status` — на `needs_evidence`, отсутствующий `metric_type` —
на `иное`, отсутствующие `number` и `currency` — на `null`. Каждое
исправление попадает в `warnings` с именем файла и количеством
смягчённых полей. Если после смягчения схема всё ещё не проходит,
этап возвращает ошибку с перечнем проблемных полей.

#### 4.7.2. rolesResponseSchema (промт roles)

Назначение: оценка кандидата под целевые роли (этап 5).

Форма: `{ roles: [...] }`. Поля: `role_id`, `scores` (6 метрик
0..10: experience_fit, responsibility_level, measurable_results,
keyword_fit, hr_screen, hiring_manager), `total`, `strengths[]`,
`gaps[]`, `overpositioning_risk` (0..10), `recommendation`.

#### 4.7.3. resumeResponseSchema (промты generation_*)

Назначение: генерация версии резюме (этап 7). Три промта:
generation_sales, generation_salesops, generation_aipo — одна
схема на всех.

Форма: `title`, `specialization`, `employment_type`, `work_format`,
`experience_total`, `experience_as_of`, `about`, `jobs[]`,
`skills[]` (`{ skill, skill_id }`), `languages[]`. Поля job:
`job_id`, `company`, `industry`, `position`, `period`, `duration`,
`context`, `actions[]`, `results[]`,
`total_experience_inconsistent`, `total_experience_note`.

Каждый result обязан иметь `fact_id` (min 1) — иначе число
не трассируется к факту и блокируется верификацией.
`hedge_present: bool` фиксирует наличие оговорки рядом с числом.

#### 4.7.4. verificationResponseSchema (промт verification)

Назначение: слой 2 верификации (этап 8, дополнение к коду).

Форма: `{ checks: [...], unsupported_skills: [], forbidden_words_found: [] }`.
Поля check: `number`, `claim`, `matches_fact`, `fact_id`
(или null), `matches_role`, `has_hedge`, `verdict`, `comment`.
`verdict`: ok | unsupported_number | wrong_role | missing_hedge |
is_target_metric.

#### 4.7.5. Реестр промтов

Все id промтов и их версии:

- extraction v1
- roles v1
- generation_sales v1
- generation_salesops v1
- generation_aipo v1
- verification v1

Файлы промтов: `config/prompts/<id>.v<version>.md`.
Загрузчик: `src/llm/prompts.ts` (`loadPrompt`, `listPrompts`).
Реестр: `src/llm/prompt-registry.ts`, функция `getPromptSpec(id)`.

## 5. Подготовка текста перед LLM

Исходные файлы (HTML-выгрузки, docx, pdf) содержат разметку
и служебные символы, которые мешают LLM. Перед отправкой текст
очищается и, если превышает лимит контекста, нарезается на чанки.

### 5.1. Очистка текста

Реализация: `src/pipeline/stage2/clean-text.ts`, функция
`cleanForLlm(text)`.

Что убирается:

- атрибуты `class="..."` и `id="..."`
- оставшиеся HTML-теги `<...>`
- множественные пробелы
- множественные переносы строк (3+ -> 2)
- BOM-символы

Что сохраняется:

- текст резюме, цифры, даты, названия компаний
- структура абзацев

Для markdown и plain text функция работает как no-op.

### 5.2. Порог чанкинга

По умолчанию 60 000 символов (параметр `chunkThreshold`).
Если текст меньше — отправляется целиком одним вызовом.

### 5.3. Нарезка

Реализация: `src/pipeline/stage2/chunk.ts`, функция
`chunkText(text, maxChars)`.

Правила:

- нарезка по абзацам (разделитель `\n\n`)
- абзацы собираются в чанк, пока сумма не превысит `maxChars`
- перекрытие 10%: последние 10% предыдущего чанка добавляются
  в начало следующего
- если отдельный абзац больше `maxChars` — жёсткая нарезка
  по символам

### 5.4. Слияние результатов

После обработки всех чанков утверждения одного файла объединяются.
Дедупликация по нормализованной цитате (trim + lowercase).
При конфликте `source_file` — первый выигрывает.
ID пересобираются по порядку: claim1, claim2, ...
